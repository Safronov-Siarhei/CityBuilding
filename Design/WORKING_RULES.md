# How to work on CityBuilding with the user — every rule in one place

For ANY AI (or person) picking up this project. These are the user's own rules, gathered from
`.claude/memory/feedback_*.md` (each rule's full story — when and why it was said — is there).
`CLAUDE.md` holds the short version; this file is the complete one. Where to find everything else:
see the map at the bottom.

## Talking to the user
- **Reply in Russian, always** — every message, buttons, questions, summaries.
- Sizes in **map cells** (hero ≈ 0.8 cell, a building 1–2 cells), never metres. A dungeon was once
  built 2.3x too big from a metre misunderstanding.
- **«Дёшево» means "not enough detail"**, NOT "add gold/luxury". Keep the skin, add detail; if unclear,
  ask which element and what is missing.
- Anything the user must copy (sheet rows, data blocks, long snippets) goes as an attached **FILE**, never
  as chat text — they cannot copy from the chat.
- Playtest lists: do **EVERY item**, and check each fix in the code path that actually runs (the user
  was angry once when a fix went into the wrong function). Keep a status-per-item note while working.

## Before building anything visual
- **New models and animations go to the user as renders for approval BEFORE they enter the game**, even
  when the user says «потом посмотрим вместе». Pilot a few, get approval, then the rest.
- **Cutscenes are discussed (beats, shots) before they are built.**
- Ideas the user only "noted" (PvP, lane mode, whirlpool, water tower, roulette…) are NOT to be built
  until the user says so — see `Design/features/ideas.md`.
- Do not copy existing games (Kingdoms & Castles etc.): take simplicity + juicy saturated colour; the
  art brief is in `Design/features/art-pipeline.md`.
- Dungeons are built like the island maps (relief, colour zones, decor kit), bright Warcraft-like —
  never a grid of cubes.

## Data, numbers, text
- **No gameplay numbers and no player-facing text in C#.** Numbers → balance CSV / Google Sheet →
  BalanceConfig; text → localization CSV + the sheet's text tabs. Campaign numbers live in
  `Assets/_Project/Campaign/*.json`. See `Design/features/balance-and-localization.md`.
- Edit the sheet yourself (Google Sheets API / connector; the browser as fallback): sheet id
  `1eroe1LMQCrpFtP4se7Oae4pGv-aOrHiqYAMdWKxxook`. Procedure and traps: `.claude/skills/balance-sheet/SKILL.md`.
  The repo CSV first, then the sheet, then verify (`.claude/skills/balance-sheet/scripts/verify_sheet.py`).
- A cell starting with `+ - =` must be written with a leading apostrophe (else it becomes a formula).
- Before release: check every language's texts fit their boxes.

## Building, testing, committing
- The whole game is generated by `Assets/_Project/Scripts/Editor/SetupProject*.cs` in Unity batchmode.
  Run Unity only through `Tools/research/run.ps1 -Steps ...` (setup, mission, editmode, playmode,
  `-Filter X`, `-Graphics`) and read its short report; open `RunLogs/` only with grep.
- **Fewer checks than edits** (strict since 2026-11-04): a small edit gets no build and no test; build
  (`-Steps setup`) after a batch of edits or when a task is done; `setup` TWICE only when Editor code
  changed (`Scripts/Editor/`). One general test run after a substantial body of work, in the background.
  No tests for models/colours/sizes/texts/UI layout/balance numbers, no photo tests, no re-run after a
  green, no re-run of a known flaky test. A new test only for a new game rule or a fixed bug.
- A test that never failed proves nothing: for a bug's regression test, break the fix once, see it go
  red with the right message, restore.
- **Never build an APK/Windows build unless the user asks in that message.** Builds go to `D:\Builds CB`
  (previous build deleted first) and are sent to Telegram by the build scripts automatically
  (token from the `TELEGRAM_BOT_TOKEN` environment variable — never in files).
- **After every commit, push to `origin master` at once** (no need to ask). Before work: `git fetch`;
  the project is worked on from two devices (`git config core.safecrlf false` once per device).
  On a pull conflict in a generated file (prefabs, BalanceConfig.asset…), take upstream.
- **The repo is PUBLIC** — nothing secret in commits (tokens, passwords, personal data).
- Mobile first: weigh frame time and GC in every design and implementation decision.

## Keeping the project's memory
- After every finished task, update the touched feature card(s) in `Design/features/` (status, rules
  the user decided, files, traps, open items); a new feature gets a card + a row in its README.
- Also update the AI memory notes in `.claude/memory/` as if the chat closes now (the user opens new
  chats to save tokens and should never have to say «сохрани контекст»). The repo copy is the durable
  one: after changing notes run `python Tools/memory_sync.py` (two-way, newer wins; `--to-local`
  restores a fresh machine, `--to-repo` pushes local notes in).
- Invasion-mode changes and decisions are also logged in `Design/Invasion.md`.
- After Blender work: `python Tools/blend_sync.py` (the Drive working folder -> `Blender/` in the repo)
  and commit `Blender/` — the repo holds the sources too (outside Assets/, never in a build).
