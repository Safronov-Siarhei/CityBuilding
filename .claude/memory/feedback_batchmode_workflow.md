The entire Unity project at D:\Fork\CityBuilding (scenes, prefabs, ScriptableObjects, materials, UI) is procedurally generated/regenerated by a single Editor script, `Assets/_Project/Scripts/Editor/SetupProject.cs`, run through Unity's CLI in batchmode — not hand-built in the Editor UI. There is no "just tweak a prefab in the Inspector" path; every visual or data change has to go through code in that script.

**Standard workflow for any change, established over many sessions**:
1. Check `Get-Process Unity` first (PowerShell). If Unity Editor is open, ask the user to close it first (batchmode conflicts with a running Editor instance) and wait for their confirmation before proceeding.
2. Edit the relevant `.cs` files.
3. Run the batchmode rebuild in the background (never poll — wait for the completion notification):
   `"<UnityPath>/Unity.exe" -batchmode -nographics -projectPath "D:/Fork/CityBuilding" -executeMethod CityBuilder.EditorTools.SetupProject.Run -quit -logFile "D:/Fork/CityBuilding/unity_build.log"`
4. Grep the log for `error CS|Exception`; spot-check regenerated scene/asset YAML for non-zero fileID references if something structural changed.
5. `git add -A -- Assets/_Project`, commit with a descriptive message, then push — see [[feedback_auto_push]] for the standing push-without-asking instruction.

**Why**: this is not optional scaffolding, it's the actual build system for the game's content — skipping the batchmode rebuild step means the edited code never actually takes effect in the scenes/prefabs the user sees.

**How to apply**: default to this loop for every gameplay/UI/data change in this repo, including when invoked headlessly (e.g. via the Telegram bridge, see [[telegram-bridge-tool]]) where there's no interactive user to catch a skipped step.

**How long a run actually takes (measured 2026-08-18):** an INCREMENTAL build is ~70 s and a test pass ~30-60 s. The 15-20 minutes quoted elsewhere is a COLD build (fresh Library, or the first PlayMode run with graphics, which re-imports every shader). Do not schedule a session around the cold number; do check the results XML's `start-time` rather than trusting elapsed time either way.

Working scripts for both loops are kept in the repo at `Tools/research/` (untracked): `retest.ps1` (EditMode then PlayMode), `build_and_test.ps1` (double build then both suites), `rebuild_and_test.ps1` (SetupProject.Run, then EditMode, then PlayMode — the everyday loop, about 2,5 minutes warm) and `playmode_only.ps1` (a compile pass plus PlayMode, about a minute, for when no CSV changed).

**An edit to the EDITOR assembly needs the SetupProject pass itself run twice** (2026-08-18): `rebuild_and_test.ps1` runs SetupProject once, so after touching `BalanceImporter` or `SetupProject` the generated asset is built by the OLD importer while the tests then run the NEW code — which looks exactly like a data bug. Run the script twice, or chain two SetupProject launches ahead of the tests.

**Batchmode gotchas learned the hard way**: (1) the FIRST Unity invocation after any .cs edit compiles the new assembly but RUNS THE OLD ONE -- always invoke twice and read the second run's results, or you will diagnose a phantom. (2) `-nographics` makes the minimap RenderTexture log an error the runner counts as a test failure; set `LogAssert.ignoreFailingMessages = true` in `[UnitySetUp]`. (3) Chained Unity invocations in one command sometimes exit 1 immediately (previous instance still releasing the project lock) -- check that the results XML timestamp actually moved. (4) PlayMode runs drop an `Assets/InitTestScene<guid>.unity` scratch scene; it is now gitignored.

**A full `SetupProject.Run` leaves ~130 files "modified" that nobody edited (learned 2026-08-14):** regenerating the project reassigns every object's `fileID`, so materials, prefabs, ScriptableObjects, textures and both scenes all re-serialize (the `CityBuilder.unity` diff alone is ~38k lines, and diff pairs up unrelated objects so it *reads* like real edits — it isn't). **The project's convention is to commit all of it** (`636e314` = 154 files, `193512c` = 133) — `git add -A -- Assets/_Project` is right whenever the run changed any generated output. Reverting the churn (`git checkout -- Assets/_Project/Materials Assets/_Project/Prefabs Assets/_Project/Scenes Assets/_Project/ScriptableObjects Assets/_Project/Textures`) is only for the case where the run changed *nothing* real and you want a readable diff (done in `be1faf5`). Never revert it partially: `BuildingData.prefab` stores the prefab's freshly randomised `fileID`, so keeping the assets while reverting the prefabs leaves dangling references.

**Verifying a refactor of generated assets:** diff them field-by-field against `git show HEAD:<path>` in a script rather than reading the churn — parse the YAML into scalars plus sorted cost lists, and compare ignoring `prefab:` fileIDs. That is how the buildings migration (`193512c`) was proven value-identical to its predecessor.

**Two traps that have each cost a wasted run — read before writing a build command:**
1. **Do not poll the process list at all — wait on the process you started.** `Start-Process -FilePath $unity -ArgumentList $args -PassThru -Wait` is the whole answer, and it also hands back the real exit code. The polling approach this file used to recommend (`while (Get-CimInstance Win32_Process ... CityBuilding) { sleep }`) is WORSE THAN NOTHING and cost a full wasted chained run on 2026-08-18: a second after launch Unity is not in the process list yet, the loop sees an empty result and returns instantly, so every later step in the chain collided on the project lock and reported four instant failures that looked like compile errors. If you must filter by project anyway (e.g. waiting on something you did not launch), the user's own Editor is usually open on `D:\Fork\AC` and a batchmode run on another project does NOT block this one — the lock is per project.
1b. **Every SetupProject run dirties ~188 generated assets with NEW RANDOM fileIDs** (2026-08-18) — sprites, prefabs, icons, ~33k lines of pure churn with no behaviour in it. Worse, the PlayMode pass rewrites them AGAIN after the SetupProject pass, so a commit made straight after reading the results can leave the tree dirty a minute later. Commit it and move on; every past commit in this repo carries the same noise. Do not mistake it for a real diff, and do not claim a clean tree without checking after the last Unity process has exited.
1a. **Killing Unity mid-run WEDGES the waiting script (2026-08-18).** `Start-Process -Wait` waits on the whole process tree, and Unity leaves helper processes (Package Manager server, asset import workers) alive after the main process dies — so the launcher sits there forever with no Unity running and no progress. Symptom: the run's output stops after one `=== label ===` line and the log file's mtime goes cold. Kill the launching powershell.exe too, then start over. (When looking for it, note a `Where-Object { $_.CommandLine -like '*rebuild*' }` filter MATCHES YOUR OWN QUERY, so it always reports one more than exists.)
2. **The shell returns before Unity exits.** A background command reporting "completed, exit code 0" routinely fires while Unity is still running, so the next invocation dies on the project lock and leaves the results XML stale at the previous run's numbers. Chain build+test inside ONE command with the project-filtered wait between them, and always confirm the XML's `start-time` is fresh.

Also: reading the same file through different tools can return different contents (a stale cache). `[System.IO.File]::ReadAllText` in PowerShell was the reliable reader for test XML.

**Detecting a running Editor properly (learned 2026-08-14):** `Get-Process Unity` is not enough to tell whose Unity is running. A batchmode run of your own leaves `AssetImportWorkerHW*` child processes that look identical in the process list, and the user's Editor may be open at the same time. Check the command lines instead — `Get-CimInstance Win32_Process -Filter "Name='Unity.exe'"` — the real Editor is the one launched with `-useHub -hubIPC` (no `-batchMode`). Never kill Unity processes to free the project lock without checking this first: on 2026-08-14 three hung processes turned out to include the user's open Editor, and killing it would have cost their unsaved work. When the Editor is open, batchmode runs exit immediately with code 1 and a 25-line log ending in "Exiting without the bug reporter", and the results XML silently stays stale — always confirm the run's `start-time` attribute is fresh before trusting a test result.

**Correction (2026-10-14): `Start-Process -Wait` itself WEDGED** — after a compile-error run Unity exited in 10 s but the launcher sat for 5+ min (it waits on the whole process tree, and helpers outlive Unity). What works: `$p = Start-Process ... -PassThru; $p.WaitForExit()` — waits for Unity alone. The repo's `Tools/research/rebuild_twice_and_test.ps1` still uses `-Wait`; a fixed copy with steps/filter/-Graphics switches lived in the session scratchpad (`run.ps1 -Steps setup,setup,editmode,playmode [-Filter X] [-Graphics]`).
